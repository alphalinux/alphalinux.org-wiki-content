===== Why Alpha Has libc.so.6.1 =====

Every other Linux architecture that uses glibc 2.x has ''libc.so.6''. Alpha has ''libc.so.6.1'', and ''libm.so.6.1'' with it. The dynamic linker, ''ld-linux.so.2'', was not renamed.

The reason is an ABI break in January 1997, when several fundamental types changed size on Alpha. Alpha had already shipped binaries against ''libc.so.6''; those binaries could not be allowed to load the new library, so the soname was changed. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-January.mbox#L26971|"Re: glibc upgrade advice?"]], Richard Henderson, axp-list, 23 Jan 1997)]

==== The Change ====

The soname bump was made by **Richard Henderson** on **18 January 1997** and imported into the glibc repository two days later.

The ChangeLog entry, excerpted (it also contains an unrelated ''config.make.in'' hunk):

<code>
Sat Jan 18 22:15:26 1997  Richard Henderson  <rth@tamu.edu>

	* shlib-versions: alpha-*-linux-* libc=6.1.

	Since sigset_t no longer fits in a register, we can't pass in the
	thread's initial mask so easily.  Take this opportunity to simplify
	the clone implementation by only accepting a single void* argument.

	* sysdeps/unix/sysv/linux/alpha/clone.S: Only take one argument.
	* sysdeps/unix/sysv/linux/i386/clone.S: Likewise.
	* sysdeps/unix/sysv/linux/m68k/clone.S: Likewise.
	* sysdeps/unix/sysv/linux/sparc/clone.S: Likewise.
	* sysdeps/unix/sysv/linux/schedbits.h: Update clone prototypes.
</code>

The actual change to ''shlib-versions'' is a one-line regex edit:

<code diff>
 # We provide libc.so.6 for Linux kernel versions 2.0 and later.
 i.86-.*-linux.*		libc=6
 m68k-.*-linux.*		libc=6
-alpha-.*-linux.*	libc=6
+alpha-.*-linux.*	libc=6.1
</code>

Note what is //not// changed: i386 and m68k keep ''libc=6'' in the very same hunk, even though their ''clone.S'' was rewritten in the same commit. Only Alpha's soname moved.

==== Why: Basic Types Changed Size ====

The ChangeLog sentence about ''sigset_t'' is terse and has been widely over-read. Richard Henderson gave the fuller reason on the Alpha list five days later, answering a user whose binaries had stopped working: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-January.mbox#L26971|"Re: glibc upgrade advice?"]], Richard Henderson, axp-list, 23 Jan 1997)]

<blockquote>
<blockquote>
Numerous existing utilities are (apparently) hard-coded into requiring libc.so.6, while the new glibc is libc.so.6.1.
</blockquote>

Indeed.  Programs remember what version of the library that they were compiled against.  As of the 970104 snapshot, several of the basic types like sigset_t and dev_t changed size, and sanity required that the library version be changed.
</blockquote>

In a later message he gave the sizes: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-May.mbox#L5740|"Re: Glibc 2.0.3 and LibX11"]], Richard Henderson, axp-list, 5 May 1997)]

<blockquote>
Several fundamental types were changed to accomodate expected needs in the near future: dev_t is now 64-bits wide, and sigset_t is now 1024 bits wide.

I'm actually surprised to hear that it works.
</blockquote>

So the cause was **a set of basic-type size changes**, of which the ''clone()'' rework is the most visible symptom, not the root. Philip Blundell summarized the practical position in the same thread: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-January.mbox#L26756|"Re: glibc upgrade advice?"]], Philip Blundell, axp-list, 23 Jan 1997)]

<blockquote>
lib.so.6.1 is not just a minor release of libc.so.6.  The soname is different because incompatible changes have happened.  Your binaries will not work if you try to use libc.so.6.1 as libc.so.6, or vice versa.
</blockquote>

=== What the clone() change was ===

The old prototype took a variable number of arguments to be copied onto the new thread's stack:

<code c>
/* before */
extern int __clone (int (*__fn) (void *, ...), void *__child_stack,
                    int __flags, int __nargs, ...);
</code>

The new one takes a single ''void *'':

<code c>
/* after */
extern int __clone (int (*__fn) (void *__arg), void *__child_stack,
                    int __flags, void *__arg);
</code>

The same commit also put the public ''clone'' declaration behind ''%%#ifdef __USE_MISC%%''. On the Alpha side, ''clone.S'' lost its varargs copying loop and its 16-byte stack frame, and ''thread_start'' lost the computed-jump block that reloaded the argument registers. That is the bulk of a 54-line diff.

=== A caution about sigset_t ===

It is often claimed that Linux's ''sigset_t'' grew past a register on Alpha. It did not, and the numbers usually quoted are wrong.

  * The **kernel's** ''sigset_t'' on Alpha is a single 64-bit word. ''arch/alpha/include/asm/signal.h'' defines ''_NSIG'' as 64, ''_NSIG_BPW'' as 64 and therefore ''_NSIG_WORDS'' as 1. It fits in one register. [(>[[https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/alpha/include/asm/signal.h|arch/alpha/include/asm/signal.h]] and [[https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/alpha/include/uapi/asm/signal.h|uapi/asm/signal.h]], Linux)]
  * ''_NSIG'' is 64 on every Linux architecture except MIPS, where it is 128. "''_NSIG'' is 128 on Linux" is simply false.
  * **glibc's** userspace ''sigset_t'' was never register-sized. It was already 1024 bits before this commit. What the commit changed was the word type, from ''unsigned int'' to ''unsigned long'':

<code diff>
-/* A `sigset_t' has a bit for each signal.  Having 32 * 4 * 8 bits gives
-   us up to 1024 signals.  */
-#define _SIGSET_NWORDS	32
+#define _SIGSET_NWORDS	(1024 / (8 * sizeof (unsigned long int)))
 typedef struct
-{  unsigned int __val[_SIGSET_NWORDS];  } __sigset_t;
+  {  unsigned long int __val[_SIGSET_NWORDS];  } __sigset_t;
</code>

The same commit rewrote Alpha's ''sigprocmask.c'', with the ChangeLog note "The osf_sigprocmask system call wants the sigset dereferenced."

Read in that light, Henderson's sentence is a rationale for //not adding// an initial-signal-mask parameter to ''clone()'', rather than a description of code being removed. The pre-change Alpha ''clone.S'' copies ''nargs'' generic quadwords to the child stack; it has no signal-mask handling at all.

==== Which Release ====

The change was on the trunk from 20 January 1997 and the version was bumped to 2.0.1 eight days later, in commit ''831372e7c1'' ("update from main archive 970127"), so it shipped in **glibc 2.0.1**. [(>[[https://sourceware.org/git/?p=glibc.git;a=commit;h=831372e7c1|"update from main archive 970127"]], glibc, 28 Jan 1997)]

It is often stated that it first shipped in 2.0.2. That is an artifact of the git mirror: there is no ''glibc-2.0.1'' tag (nor ''glibc-2.0.3''), so ''git describe --contains'' finds ''glibc-2.0.2'' as the earliest release tag. CVS-era tag dates are not reliable as release dates either; the commit that ''glibc-2.0.4'' points at is dated earlier than the one ''glibc-2.0.2'' points at.

Independent corroboration that 6.1 was in users' hands well before March 1997: the axp-list thread quoted above is dated 23 January 1997, and the user was already running a snapshot that produced ''libc.so.6.1''. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-January.mbox#L26633|"glibc upgrade advice?"]], Steven N. Hirsch, axp-list, 23 Jan 1997)]

==== What Was Not the Cause ====

Two claims that circulate about this and do not survive checking.

=== It was not the ioctl encoding ===

Alpha's ioctl command numbers do follow OSF/1 conventions rather than the generic Linux layout, and ''sysdeps/unix/sysv/linux/alpha/bits/ioctls.h'' does exist. But that header exists because of a ''struct termios'' size mismatch, not the command-number encoding, and it says so itself:

<code c>
/* Use the definitions from the kernel header files.  */
#include <asm/ioctls.h>

/* Oh well, this is necessary since the kernel data structure is
   different from the user-level version.  */
#undef  TCGETS
...
#define TCGETS	_IOR ('t', 19, char[44])
</code>

It //includes// the kernel's ''<asm/ioctls.h>'', deferring to the kernel's encoding rather than reimplementing it. It also does not predate the bump: it was added on 23 January 1997, three days after. (The soname commit did remove ''sysdeps/unix/sysv/linux/alpha/ioctl-types.h'', as part of the same ABI churn.)

=== IA-64 used 6.1 for a different reason ===

IA-64 also used ''libc.so.6.1'' and ''libm.so.6.1'', and it is tempting to assume the same cause. It is not. IA-64 support entered glibc at ''GLIBC_2.2'' already using 6.1, so it never shipped a ''libc.so.6'' and had no break to signal. Why it chose 6.1 is not documented anywhere in the tree. IA-64 has since been removed from glibc, leaving Alpha as the only architecture using 6.1:

<code>
$ git grep -n "libc=6.1" -- '*shlib-versions*'
sysdeps/unix/sysv/linux/alpha/shlib-versions:2:libc=6.1
</code>

<code>
$ cat sysdeps/unix/sysv/linux/alpha/shlib-versions
libm=6.1
libc=6.1
ld=ld-linux.so.2
...
</code>

==== Aftermath ====

The transition was painful, because the whole system had to be rebuilt against a library that existing binaries could not load. Henderson's advice at the time was to do it in a chroot containing statically linked ''bash'', ''make'', ''gcc'' and ''binutils''. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-January.mbox#L26971|"Re: glibc upgrade advice?"]], Richard Henderson, axp-list, 23 Jan 1997)] Ulrich Drepper, in the same thread: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-January.mbox#L27530|"Re: glibc upgrade advice?"]], Ulrich Drepper, axp-list, 23 Jan 1997)]

<blockquote>
For Alpha probably all number must be increased. It must not be a problem and since most people running Linux/Alpha today will probably have a RedHat based system the update will hopefully remove all references to the old libc and other libs so that these can be removed soon.
</blockquote>

A year later, users were still hitting it as the Red Hat 4.x to 5.0 upgrade. Henderson, February 1998: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1998-February.mbox#L18518|"Re: Explain Compilers Libc and Glibc, and what is causing the Probs."]], Richard Henderson, axp-list, 21 Feb 1998)]

<blockquote>
The libc shipped with RH 4.x was not an official release of glibc, and is not binary compatible with the 2.0 release of glibc. Those are the breaks for using snapshots.

In order to catch problems that this incompatibility would cause, the sonames of the libraries were changed from e.g. 6.0 to 6.1.
</blockquote>

Thirty years on, the ''.1'' is still there. Nothing about current Alpha glibc requires it; it is a fossil of a 1997 snapshot ABI, kept because changing it back would break every Alpha binary ever built.
