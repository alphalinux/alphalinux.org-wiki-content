===== Unaligned Access =====

Unaligned memory access is the most common reason software fails when first built for Alpha. Every Alpha load and store except ''LDQ_U'' and ''STQ_U'' traps when the address is not a multiple of the operand size, and no implementation corrects the access in hardware.

The construct responsible is almost always a pointer cast such as ''%%*(uint32_t *)(buf + 1)%%''. It is undefined behavior in C on every target, including x86, where the hardware ordinarily tolerates it; the sections below include an x86-64 program that fails because of it. Alpha differs from such targets only in reporting the error immediately.

See also [[documentation:porting:byte_word_access|Byte and Word Access]] and [[documentation:porting:memory_model|Memory Model]].

==== What counts as aligned ====

An access is //aligned// when the address is a multiple of the operand size.

^ Instruction ^ Operand ^ Required alignment ^
| ''LDBU'' / ''STB'' | byte | any address |
| ''LDWU'' / ''STW'' | word, 16-bit | address % 2 == 0 |
| ''LDL'' / ''STL'' | longword, 32-bit | address % 4 == 0 |
| ''LDQ'' / ''STQ'' | quadword, 64-bit | address % 8 == 0 |
| ''LDS'' / ''STS'' | S_floating, 32-bit | address % 4 == 0 |
| ''LDT'' / ''STT'' | T_floating, 64-bit | address % 8 == 0 |
| ''LDQ_U'' / ''STQ_U'' | quadword | none; address bits <2:0> are ignored |

''LDBU'', ''LDWU'', ''STB'' and ''STW'' are the Byte/Word Extension (BWX, ''amask'' bit 0), introduced with the 21164A (EV56). No Alpha has an ''LDB'' or ''LDW'' instruction. Earlier parts have no byte or word memory instructions at all; see [[documentation:porting:byte_word_access|Byte and Word Access]].

Every load and store except ''LDQ_U''/''STQ_U'' faults on an unaligned address. From the Architecture Reference Manual, on ''LDS'':

<blockquote>
If the data is not naturally aligned, an alignment exception is generated.
</blockquote>

The same sentence appears for ''LDT'', ''STS'' and ''STT''.

No Alpha implementation fixes unaligned accesses up in hardware. The unaligned data reference is an architecturally defined trap on every part from the 21064 to the 21364.

BWX does not change this. It adds byte and word instructions; it does not make misaligned longword or quadword access work.

==== What Alpha does at runtime ====

An unaligned load or store traps to PALcode, which reflects the trap to the kernel. User-space accesses are handled by ''do_entUnaUser()'' in ''arch/alpha/kernel/traps.c''; kernel-mode accesses go to ''do_entUna()'' in the same file, which fixes up only accesses covered by an exception-table entry and otherwise panics.

By default the kernel emulates the access, logs a message, and lets the process continue. The behavior is controlled per process by three bits:

<code c>
#define UAC_BITMASK			7
#define UAC_NOPRINT			1
#define UAC_NOFIX			2
#define UAC_SIGBUS			4
</code>

=== The log message ===

<code c>
			printk("%s(%d): unaligned trap at %016lx: %p %lx %ld\n",
			       current->comm, task_pid_nr(current),
			       regs->pc - 4, va, opcode, reg);
</code>

^ Field ^ Meaning ^
| ''%s(%d)'' | process name and PID |
| ''%016lx'' | address of the faulting instruction (the trap PC points past it, hence the ''- 4'') |
| ''%p'' | the unaligned virtual address |
| ''%lx'' | the memory-format opcode, in **hex**: ''28''=LDL, ''29''=LDQ, ''2c''=STL, ''2d''=STQ |
| ''%ld'' | the instruction's Ra register number, in **decimal**. This is the destination of a load or the source of a store. It is not a cause code. |

Two properties of the message limit its use:

  * The ''%p'' address is hashed on any modern kernel unless it is booted with ''no_hash_pointers''. The instruction address is real; the data address is not.
  * The message is rate limited to 5 per 5 seconds. A hot loop loses almost all of them, so ''dmesg'' output cannot be used to count occurrences.

=== Counting them properly ===

Alpha exports cumulative, un-rate-limited counters:

<code>
$ grep unaligned /proc/cpuinfo
kernel unaligned acc	: 0 (pc=0,va=0)
user unaligned acc	: 1174 (pc=120001234,va=11ffff8e5)
</code>

Sampling these counters before and after a run shows whether a program performed any unaligned access.

=== Making it fatal ===

The portable interface works on Alpha:

<code c>
#include <sys/prctl.h>

/* SIGBUS on any unaligned access in this process */
prctl(PR_SET_UNALIGN, PR_UNALIGN_SIGBUS, 0, 0, 0);

/* fix up silently: no log message, no signal */
prctl(PR_SET_UNALIGN, PR_UNALIGN_NOPRINT, 0, 0, 0);
</code>

''PR_SET_UNALIGN'' replaces the mask rather than OR-ing into it. Alpha also accepts a third bit, bare value ''4'', mapping to ''TS_UAC_NOFIX'' ("do not fix up at all"), which has no ''PR_UNALIGN_*'' name. The kernel's own comment on it reads ''/* Not sure why you'd want to use this, but... */''.

The Alpha-specific interface inherited from Digital UNIX is ''osf_setsysinfo()''. glibc does not wrap it, so it must be invoked directly:

<code c>
#include <asm/sysinfo.h>
#include <sys/syscall.h>
#include <unistd.h>

unsigned int buf[2] = { SSIN_UACPROC, UAC_SIGBUS };
syscall(__NR_osf_setsysinfo, SSI_NVPAIRS, buf);
</code>

The two interfaces assign different meanings to the same bit values: the value 2 is ''UAC_NOFIX'' to ''osf_setsysinfo()'' and ''PR_UNALIGN_SIGBUS'' to ''prctl()''.

Richard Henderson implemented this interface in the 2.1 kernels, cloned from Digital UNIX's ''setsysinfo(2)''. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1997-October.mbox#L4654|"Re: Unaligned Traps - have they been turned off !!!!"]], Richard Henderson, axp-list, 6 Oct 1997)] Only the per-process ''SSIN_UACPROC'' case was implemented, not Digital UNIX's system-wide ''SSIN_UACSYS'' or per-parent ''SSIN_UACPARNT''. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/1999-August.mbox#L27175|"Re: Unaligned traps et al"]], Richard Henderson, axp-list, 18 Aug 1999)]

Setting one of these at the top of ''main()'' in a test harness turns every unaligned access into a core dump with a usable backtrace instead of a line in ''dmesg''.

=== Absence of a sysctl ===

Some guides suggest ''echo 2 > /proc/sys/kernel/unaligned-trap''. It does not apply to Alpha. The ''unaligned-trap'' sysctl exists only on architectures that opt in to it (parisc, arc, loongarch and riscv), takes only the values 0 and 1, and is not available on Alpha, which registers no sysctls of its own. Alpha's only controls are the two per-process interfaces described above.

=== The same controls on other operating systems ===

Every Alpha operating system fixes user unaligned accesses up by default, prints a warning and lets the program continue, and each provides a way to change that behavior. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/netbsd-port-alpha-mbox/1998-May.mbox#L2901|"Re: unaligned access"]], Chris G. Demetriou, port-alpha, 19 May 1998)] [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/freebsd-alpha-mbox/1999-April.mbox#L7696|"Re: egcs ready for alpha?"]], Andrew Gallatin, freebsd-alpha, 18 Apr 1999)]

^ Operating system ^ Control ^ Scope ^
| Linux | ''prctl(PR_SET_UNALIGN)'', ''osf_setsysinfo(SSIN_UACPROC)'' | per process |
| NetBSD, FreeBSD | ''machdep.unaligned_print'', ''machdep.unaligned_fix'', ''machdep.unaligned_sigbus'' | system wide |
| Digital UNIX, Tru64 UNIX | ''uac''(1), ''setsysinfo()'' with ''SSIN_UACPROC'', ''SSIN_UACPARNT'' or ''SSIN_UACSYS'' | per process, per parent, system wide |

On every one of these systems the message indicates a defect in the program, whose cost the kernel pays on each execution of the instruction. Silencing the message does not remove that cost.

==== What an unaligned access costs ====

Reliable per-instruction figures are not available. In 2008 Jay Estabrook reported that rendering a single web page with Ghostscript incurred over 200 million unaligned accesses, and that fixing them reduced the render time from more than 30 seconds to one or two seconds. [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/2008-May.mbox#L2761|"Getting rid of Unaligned Accesses (UA)"]], Jay Estabrook, axp-list, 23 May 2008)] Disabling the log messages does not remove the cost of the traps. [(>"Re: Turning off 'unaligned trap' logging", Jay Estabrook, axp-list, 8 Nov 2000)]

The cost has the following structure. A fixed-up unaligned access pays for, at minimum: the PALcode unaligned trap; entry to ''do_entUnaUser()''; decode of the faulting instruction; two ''LDQ_U'' plus extract and merge for a load, or two ''LDQ_U'', mask, insert and two ''STQ_U'' for a store; a write back into the saved register file; and the return to user mode. On top of that come the instruction-cache and branch-predictor damage of the round trip, and a rate-limited ''printk'' if logging is still enabled.

The sequence is orders of magnitude more expensive than the single instruction it replaces, being a trap into the operating system rather than a pipeline stall.

A figure for particular hardware can be obtained with an ''rpcc''-timed loop comparing aligned against ''+1''-offset accesses, with ''UAC_NOPRINT'' set so that logging falls outside the measurement.

==== What the compiler emits instead ====

Alpha is a ''STRICT_ALIGNMENT'' target. When GCC cannot prove that a pointer is aligned, which is the default for a ''char *'' or a ''memcpy'' source, it emits the extract sequence rather than a faulting load. The Architecture Handbook gives the canonical form:

<code asm>
    LDQ_U  R1, X(R11)      ; Ignores va<2:0>, R1 = CBAx xxxx
    LDQ_U  R2, X+3(R11)    ; Ignores va<2:0>, R2 = yyyy yyyD
    LDA    R3, X(R11)      ; R3<2:0> = (X mod 8) = 5
    EXTLL  R1, R3, R1      ; R1 = 0000 0CBA
    EXTLH  R2, R3, R2      ; R2 = 0000 D000
    OR     R2, R1, R1      ; R1 = 0000 DCBA
</code>

In practice, for ''%%uint32_t v; memcpy(&v, p, sizeof v); return v;%%'', ''alpha-unknown-linux-gnu-gcc -O2'' (default ''-mcpu=ev4'') produces:

<code asm>
	ldq_u $0,0($16)
	ldq_u $1,3($16)
	extll $0,$16,$0
	extlh $1,$16,$1
	bis $0,$1,$0
	addl $31,$0,$0      /* sign-extend to canonical 64-bit form */
</code>

Six instructions instead of one. The aligned version, ''%%return *(const uint32_t *)p;%%'', is a single ''ldl''. An unaligned 32-bit //store// is worse still: two ''LDQ_U'', ''MSKLL''/''MSKLH'', ''INSLL''/''INSLH'', two ''BIS'' and two ''STQ_U''.

Six instructions is the cheaper case, in which the compiler treated the pointer as possibly misaligned. The expensive case is a plain ''LDL'', emitted because the pointer was declared ''uint32_t *'', which the hardware then traps.

Ivan Kokshaysky gave the same advice on the Alpha list in 2001: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/2001-July.mbox#L36126|"Re: Unaligned accesses"]], Ivan Kokshaysky, axp-list, 26 Jul 2001)]

<blockquote>
Using memcpy() with constant size is fine as well, and is portable. Modern GCC (>= 2.95) generates quite a good inline code for this.
</blockquote>

In an optimized build ''memcpy'' of a scalar is not a function call on any target: on x86-64 it is a single ''movl'', and on Alpha it is the sequence above. ''%%memcpy(&v, p, sizeof v)%%'' is the portable spelling of a load performed however the machine requires, and unlike the cast it is well-defined C.

==== Finding unaligned accesses ====

=== UBSan on a non-Alpha host ===

UBSan detects most alignment defects without Alpha hardware.

<code sh>
gcc -g -fsanitize=undefined -fno-sanitize-recover=alignment myfile.c -o mybinary
./mybinary
</code>

<code>
u.c:4:55: runtime error: store to misaligned address 0x561495a5f121 for type 'uint32_t', which requires 4 byte alignment
0x561495a5f121: note: pointer points here
 00 00 00  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  00 00 00 00 00
              ^
</code>

''-fsanitize=alignment'' is already part of ''-fsanitize=undefined''. ''-fno-sanitize-recover=alignment'' makes the first occurrence abort; by default UBSan prints a diagnostic and continues, which is unsuitable for a test suite.

=== -Wcast-align and -Wcast-align=strict ===

''-Wcast-align'' warns only on targets that require alignment, and is a silent no-op on x86, so on an x86 build host it reports nothing. From ''gcc/doc/invoke.texi'':

<code>
@item -Wcast-align
Warn whenever a pointer is cast such that the required alignment of the
target is increased.  For example, warn if a @code{char *} is cast to
an @code{int *} on machines where integers can only be accessed at
two- or four-byte boundaries.

@opindex Wcast-align=strict
Warn whenever a pointer is cast such that the required alignment of the
target is increased.  For example, warn if a @code{char *} is cast to
an @code{int *} regardless of the target machine.
</code>

The difference is target sensitivity. Neither variant inspects the offset; both fire on the cast, which means ''=strict'' will also warn about casts that happen to be fine. It is a lint, not a proof.

<code c>
char buf[64];
uint32_t *p(void) { return (uint32_t *)(buf + 1); }
</code>

<code>
$ gcc -c -Wcast-align x.c                        # x86-64: nothing
$ gcc -c -Wcast-align=strict x.c
x.c:3:27: warning: cast increases required alignment of target type [-Wcast-align]
$ alpha-unknown-linux-gnu-gcc -c -Wcast-align x.c
x.c:3:27: warning: cast increases required alignment of target type [-Wcast-align]
</code>

=== GDB ===

<code sh>
gdb ./mybinary
(gdb) handle SIGBUS stop print
(gdb) run
</code>

<code>
(gdb) bt
(gdb) x/i $pc                                    # the faulting instruction
(gdb) p $_siginfo.si_code                        # 1 == BUS_ADRALN
(gdb) p/x $_siginfo._sifields._sigfault.si_addr  # the misaligned address
</code>

The kernel rewinds ''$pc'' to the faulting instruction before delivering the signal, and sets ''si_addr'' to the unaligned address:

<code c>
give_sigbus:
	regs->pc -= 4;
	send_sig_fault(SIGBUS, BUS_ADRALN, va, current);
	return;
</code>

''$_siginfo'' is only populated when GDB intercepts a live signal, so this works under ''handle SIGBUS stop'', not on a core file.

=== Kernel log and addr2line ===

This method is limited by the hashing and rate limiting described above. The faulting PC is the field ending in a colon:

<code sh>
dmesg -t | sed -n 's/.*unaligned trap at \([0-9a-f]*\):.*/0x\1/p' |
sort -u | while read -r pc; do
    addr2line -e ./mybinary -f -C "$pc"
done
</code>

''addr2line'' expects a link-time address, so for a PIE or a shared library the mapping base must be subtracted first. The binary must be built with ''-g''.

==== Detection workflow ====

The steps below combine the tools described above.

  - Build with ''-g -fsanitize=undefined -fno-sanitize-recover=alignment -Wcast-align=strict''. The ''=strict'' form is required, since the plain form does nothing on x86.
  - Run the test suite on x86. UBSan finds the majority of alignment defects without Alpha hardware.
  - On Alpha, call ''prctl(PR_SET_UNALIGN, PR_UNALIGN_SIGBUS, 0, 0, 0)'' at the top of ''main()'' and run under ''gdb'' with ''handle SIGBUS stop print''.
  - Compare ''grep unaligned /proc/cpuinfo'' before and after a run as a regression check.
  - Repair the access with ''memcpy'', or with ''get_unaligned()'' in kernel code. Casting through ''void *'' silences the warning without removing the undefined behavior.

==== Common causes ====

=== Packed structures ===

<code c>
struct __attribute__((packed)) header {
    uint8_t  type;
    uint32_t length;   /* offset 1 */
    uint64_t checksum; /* offset 5 */
};
</code>

Reading ''h->length'' through a ''struct header *'' is fine, because ''__packed'' tells the compiler the field is unaligned and it emits the extract sequence. The defect is taking the //address// of a packed field and passing it on as an ordinary pointer, which discards the alignment information. GCC's ''-Waddress-of-packed-member'' diagnoses this.

=== Pointer arithmetic on byte buffers ===

<code c>
/* WRONG */
uint32_t val = *(uint32_t *)(buf + 3);

/* RIGHT */
uint32_t val;
memcpy(&val, buf + 3, sizeof val);
</code>

=== Network and file format parsing ===

Wire formats pack fields without padding, and a receive buffer offset by a header length is aligned only by chance. David Huggins-Daines, on the Alpha list in 2000: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/2000-May.mbox#L10130|"Re: Fixing 'unaligned trap' errors"]], David Huggins-Daines, axp-list, 19 May 2000)]

<blockquote>
Lots of legacy binary data formats have unaligned fields, because at the time, saving a few bytes on the 16-bit machines of the time was a higher priority than planning for 32 and 64-bit RISC machines of the future.

For example ... IP headers, DOS partition tables, DWARF2 exception frame info.

In general whenever you cast from a pointer to a smaller type to a pointer of a larger type you have a potential alignment problem. (and of course, if the smaller type is not char*, you will also have problems with strict aliasing).
</blockquote>

This is the distinction described under [[#it_is_undefined_behavior_in_c|It is undefined behavior in C]]: the alignment problem and the aliasing problem are two separate defects in the same line of code.

Alignment is also the reason network drivers on Alpha copy packets. Ivan Kokshaysky, 2001: [(>[[https://github.com/alphalinux-org/mailing-list-archives/blob/main/axp-list-mbox/2001-December.mbox#L6642|"Re: Kernel unaligned accesses"]], Ivan Kokshaysky, axp-list, 11 Dec 2001)]

<blockquote>
Yes - it's a common problem on alpha and several other platforms with network cards capable to DMA only on a 32-bit boundary (via-rhine is one of those). Without copying the packet to another buffer IP header will be misaligned, and you'll have tons of unaligned traps in the TCP/IP layer.
</blockquote>

The fix was to default ''rx_copybreak'' to the full MTU on ''__alpha__'', ''__sparc__'', ''__mips__'' and ''__arm__'', four architectures rather than Alpha alone.

<code c>
/* WRONG on Alpha, undefined everywhere */
struct ip_header *ip = (struct ip_header *)packet;
uint16_t len = ntohs(ip->total_length);

/* RIGHT */
struct ip_header ip;
memcpy(&ip, packet, sizeof ip);
uint16_t len = ntohs(ip.total_length);
</code>

=== Type punning through a union ===

<code c>
union { char bytes[8]; uint64_t qword; } u;
</code>

This is safe, and is a type-punning idiom that C (but not C++) explicitly permits. The union carries the alignment of its strictest member. Problems arise only when the union is embedded in a packed structure or placed at a computed offset.

==== In kernel code ====

Kernel code uses ''get_unaligned()'' and ''put_unaligned()'':

<code c>
#include <linux/unaligned.h>
</code>

''asm/unaligned.h'' and ''asm-generic/unaligned.h'' no longer exist; they were consolidated into ''linux/unaligned.h''.

The helpers were once implemented with a packed structure. The current implementation is based on ''memcpy'', and its comment gives the reason:

<code c>
/**
 * __get_unaligned_t - read an unaligned value from memory.
 * …
 * Use memcpy to affect an unaligned type sized load avoiding undefined behavior
 * from approaches like type punning that require -fno-strict-aliasing in order
 * to be correct. …
 */
</code>

==== It is undefined behavior in C ====

The relevant rule is about the //cast//, not the dereference. **C11/C17 §6.3.2.3 paragraph 7**:

<blockquote>
A pointer to an object type may be converted to a pointer to a different object type. If the resulting pointer is not correctly aligned for the referenced type, the behavior is undefined. Otherwise, when converted back again, the result shall compare equal to the original pointer.
</blockquote>

and **Annex J.2**, in the list of undefined behaviors:

<blockquote>
Conversion between two pointer types produces a result that is incorrectly aligned (6.3.2.3).
</blockquote>

Three consequences follow:

  - The undefined behavior occurs at the cast. ''%%(uint32_t *)(buf + 1)%%'' is undefined even if the pointer is never dereferenced, which is why ''-Wcast-align=strict'' diagnoses the cast and never examines the offset.
  - There is no exception for hardware that tolerates the access. x86 guarantees that the //hardware// will not trap on an ordinary integer load. It guarantees nothing about what the //compiler// may assume or emit.
  - The rule is distinct from strict aliasing, which is §6.5 paragraph 7, about effective types. ''%%*(uint32_t *)(buf + 1)%%'' on a ''char'' array violates both rules, and ''-fno-strict-aliasing'' disables exploitation of the aliasing rule only. It has no effect on §6.3.2.3p7.

''memcpy'' satisfies both rules at once. It accesses through character-type lvalues, which §6.5p7 explicitly permits, and it performs no misaligned pointer conversion, so §6.3.2.3p7 never engages. It is therefore the recommended construct, and compilers reduce it to the same instructions as a direct load.

==== Effects on x86 ====

=== A misaligned pointer in plain C ===

The following program uses no intrinsics, no inline assembly and no ''-ffast-math''. It uses a type that the ABI requires to be 16-byte aligned, and a pointer that is not.

<code c>
/* v.c */
typedef int v4si __attribute__((vector_size(16)));
void vcopy(v4si *d, const v4si *s) { *d = *s; }
</code>

<code c>
/* main.c */
#include <stdio.h>
typedef int v4si __attribute__((vector_size(16)));
extern void vcopy(v4si *d, const v4si *s);
static char dst[64], src[64];
int main(void) { vcopy((v4si *)(dst + 1), (v4si *)(src + 1)); printf("survived\n"); }
</code>

''gcc -O2'' compiles ''vcopy'' to aligned moves, because it is entitled to assume the pointer is aligned:

<code asm>
vcopy:
	movdqa	(%rsi), %xmm0
	movaps	%xmm0, (%rdi)
	ret
</code>

<code>
$ gcc -O2 -c v.c && gcc -O2 main.c v.o -o t && ./t; echo "exit=$?"
exit=139
</code>

<code>
Program received signal SIGSEGV, Segmentation fault.
0x0000555555555184 in vcopy ()
(gdb) x/i $pc
=> 0x555555555184 <vcopy+4>:	movdqa xmm0,XMMWORD PTR [rsi]
</code>

Exit status 139 is ''SIGSEGV''. The ''#GP'' fault from ''MOVDQA'' on a misaligned operand is delivered as ''SIGSEGV'', which is why ''si_addr'' is 0 rather than the offending address. The failure is the ordinary consequence of writing through a pointer that is not aligned as its type requires, on an architecture usually regarded as tolerant of misalignment.

=== Alignment checking on x86 ===

With the ''EFLAGS.AC'' flag set, which has been possible since the 486, x86 also traps misaligned accesses and delivers ''SIGBUS'' with ''BUS_ADRALN'', the same signal and ''si_code'' Alpha delivers. x86 software tolerates misaligned access only because the flag is normally clear.

=== Examples in the Linux kernel ===

The kernel's own ''get_unaligned()''/''put_unaligned()'' helpers relied on packed-structure type punning for years and were converted to ''memcpy'' (commit ''a339671db64b''); several other kernel fixes address the same defect in generic code. None of these are Alpha-specific defects. They are C defects that a strict-alignment target exposes first.

==== Summary of build flags ====

^ Flag ^ Purpose ^
| ''-fsanitize=undefined'' | includes the alignment check; works on any architecture |
| ''-fno-sanitize-recover=alignment'' | abort on the first misaligned access instead of printing and continuing |
| ''-Wcast-align=strict'' | diagnose alignment-increasing casts regardless of target; the form to use on x86 hosts |
| ''-Wcast-align'' | same, but only on strict-alignment targets; a no-op on x86 |
| ''-Waddress-of-packed-member'' | catch pointers taken to packed fields |
| ''-g'' | required for ''addr2line'' and useful backtraces |
